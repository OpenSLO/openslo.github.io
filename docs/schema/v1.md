# OpenSLO v1 Specification

This page describes version 1 (`openslo/v1`) of the OpenSLO specification.

## Objects

The v1 specification defines the following object types:

- [**Service**](v1/service.md) - High-level grouping of SLOs
- [**SLI**](v1/sli.md) - Service Level Indicator defining measurement methods
- [**SLO**](v1/slo.md) - Service Level Objective defining reliability targets
- [**AlertCondition**](v1alpha.md) - Alert condition configuration (see v1alpha)
- [**AlertNotificationTarget**](v1alpha.md) - Alert notification targets (see v1alpha)
- [**AlertPolicy**](v1alpha.md) - Alert policy configuration (see v1alpha)
- [**DataSource**](v1alpha.md) - Data source configuration (see v1alpha)

## Common Properties

All OpenSLO v1 objects share common properties in their structure.

### `apiVersion`

All objects must specify `apiVersion: openslo/v1`.

### `kind`

All objects must specify a `kind` field that identifies the object type (e.g., `Service`, `SLO`, `SLI`).

<a id="metadata"></a>
### `metadata`

The `metadata` section is common to all OpenSLO objects and provides identifying information and organizational tags.

Every OpenSLO object (SLO, Service, SLI, AlertPolicy, etc.) includes a `metadata` section with the following structure:

```yaml
metadata:
  name: string              # required
  displayName: string       # optional
  labels:                   # optional
    key1:
      - value1
      - value2
    key2:
      - value3
  annotations:              # optional
    key1: value1
    key2: value2
```

##### `metadata.name`

??? property "<span class='property-type-badge'>string</span> <span class='property-status-badge'>required</span>"

    Unique identifier for the object within its scope. Must be a valid DNS label name.

<a id="metadata-labels"></a>
##### `metadata.labels`

??? property "<span class='property-type-badge'>map[string][]string</span>"

    Key-value pairs used for organizing and selecting objects. Each label key can have multiple values.

    Labels are intended for organizational purposes and can be used to:

    - Group related objects
    - Filter objects in queries
    - Apply policies to sets of objects
    - Organize objects by team, environment, region, etc.

    **Example:**

    ```yaml
    labels:
      team:
        - platform
        - sre
      env:
        - production
      region:
        - us-east-1
    ```

    ---

    **Validation Rules**

    <table>
      <thead>
        <tr>
          <th>Rule</th>
          <th>Details</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td>Label keys must be valid DNS subdomain names</td>
          <td>May contain alphanumeric characters, '-', '_', and '.'. Must start and end with alphanumeric character.</td>
        </tr>
        <tr>
          <td>Label keys length: 1-63 characters (or up to 253 for prefix + 63 for name)</td>
          <td>Can use format: <code>prefix.example.com/name</code></td>
        </tr>
        <tr>
          <td>Label values must be valid label values</td>
          <td>0-63 characters, alphanumeric with '-', '_', '.'</td>
        </tr>
      </tbody>
    </table>

<a id="metadata-annotations"></a>
##### `metadata.annotations`

??? property "<span class='property-type-badge'>map[string]string</span>"

    Key-value pairs used to store arbitrary non-identifying metadata. Unlike labels, annotations are not used for selection or filtering.

    Annotations are intended for:

    - Tool-specific configuration
    - Build/release information
    - Documentation links
    - Integration metadata

    **Example:**

    ```yaml
    annotations:
      openslo.com/service-folder: ./services/api
      documentation: https://docs.example.com/api
      maintainer: platform-team@example.com
      last-updated: "2024-01-15"
    ```

    ---

    **Validation Rules**

    <table>
      <thead>
        <tr>
          <th>Rule</th>
          <th>Details</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td>Annotation keys must be valid qualified names</td>
          <td>Same format as label keys: optional prefix + name</td>
        </tr>
        <tr>
          <td>Annotation values have no length restriction</td>
          <td>Can contain any string value</td>
        </tr>
      </tbody>
    </table>

#### Labels vs Annotations

Use **labels** when:

- You need to select/filter objects
- The data is used for grouping or organization
- The values are controlled/enumerated
- You want to query objects by these values

Use **annotations** when:

- Storing tool-specific configuration
- Recording non-identifying metadata
- Storing large or unstructured data
- The data is not used for selection

#### Examples

**Minimal Metadata:**

```yaml
metadata:
  name: my-service
```

**Full Metadata:**

```yaml
metadata:
  name: payment-api-availability
  displayName: Payment API Availability SLO
  labels:
    team:
      - payments
      - platform
    env:
      - production
    criticality:
      - high
    service:
      - payment-api
  annotations:
    openslo.com/service-folder: ./services/payment-api
    runbook: https://wiki.example.com/runbooks/payment-api
    pagerduty-service-id: PD12345
    jira-component: PAYMENT-API
    cost-center: "1234"
```

**Multi-Environment Labels:**

```yaml
metadata:
  name: user-service-latency
  displayName: User Service Latency
  labels:
    env:
      - staging
      - production
    region:
      - us-east-1
      - eu-west-1
    team:
      - backend
```
